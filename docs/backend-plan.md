เอกสารลงรายละเอียดสำหรับผู้พัฒนา: [Backend Implementation Specification & Handoff](backend-implementation-spec.md)

หมายเหตุการลงรายละเอียด: สเปกใหม่เลือก API-first สำหรับข้อมูลธุรกิจทั้งหมด โดยให้ Supabase อยู่หลัง server adapter เพื่อเตรียมย้ายไป NestJS; เป็นการเจาะจงทางเลือกจากแผนภาพรวม ไม่ใช่การเริ่มพัฒนาแล้ว

## ข้อสรุปที่ตกลงกัน

- ก่อนโครงการได้รับอนุมัติ ใช้ Supabase เพื่อทำระบบทดลองกับผู้ใช้จริงได้เร็ว
- คง React + Vite + TypeScript และ editor/3D เดิม ไม่ย้าย frontend framework
- ใช้ Supabase Auth, PostgreSQL และ Storage พร้อม API TypeScript สำหรับกฎธุรกิจที่ต้องตรวจสอบฝั่ง server
- ออกแบบให้ย้ายไป NestJS + PostgreSQL + Object Storage ได้ โดยไม่ผูกโค้ดทั้งแอปกับ Supabase
- ไม่จำเป็นต้องย้ายออกทันทีเมื่อโครงการได้รับอนุมัติ ให้ประเมินความต้องการ ต้นทุน และภาระดูแลก่อน
- เพิ่ม NestJS โดยยังใช้ Supabase เป็นฐานข้อมูล ระบบบัญชี และที่เก็บไฟล์ได้ แล้วทยอยเปลี่ยนบริการทีละส่วน
- เริ่มแบบระบบเดียวที่แบ่งโมดูลชัดเจน ยังไม่ใช้ microservices

## สภาพปัจจุบันที่เป็นจุดตั้งต้น

- Login เป็นตัวจำลอง ไม่ใช่ Google OAuth จริง
- งานเก็บใน localStorage และนำเข้า/ส่งออกไฟล์โปรเจกต์ได้
- รูปประกอบบางส่วนเก็บรวมในข้อมูลโปรเจกต์แบบ data URL
- มี API เรียก AI แล้ว แต่ยังไม่มีระบบบัญชี โควตาต่อผู้ใช้ และการบันทึกต้นทุนครบถ้วน
- การคำนวณแบบ การแสดง 3D และการส่งออกไฟล์ส่วนใหญ่ทำใน browser
- ยังไม่มีระบบชำระเงินและสิทธิ์ใช้งานเชิงพาณิชย์

## การแบ่งหน้าที่

| ส่วน | ระยะแรก | แนวทางเมื่อขยายระบบ |
| --- | --- | --- |
| Editor และ 3D | React/Vite เดิม คำนวณแบบโต้ตอบใน browser | คงเดิม แชร์โค้ดคำนวณที่ไม่ผูกกับ browser กับ backend |
| บัญชีผู้ใช้ | Supabase Auth เริ่มจาก Google login | NestJS ตรวจ token เดิมได้; ย้ายผู้ให้บริการ Auth เป็นงานแยก |
| ข้อมูล | PostgreSQL บน Supabase | ย้ายไป PostgreSQL ผู้ให้บริการอื่นเมื่อจำเป็น |
| รูปและไฟล์ | Supabase Storage แบบ private | เปลี่ยนเป็น Object Storage ผ่าน adapter |
| กฎธุรกิจ | API Node.js/TypeScript ต่อจากโครงสร้างเดิม | ย้ายโมดูลเข้า NestJS โดยรักษาสัญญา API |
| งานสร้างไฟล์หนัก | ประเมินจากงานจริงก่อน | เพิ่ม worker เมื่อเกินความเหมาะสมของ request/response |

## ขอบเขตที่ต้องวางเพื่อให้ย้ายได้

1. **แยกการเข้าถึงบริการออกจาก UI**
   - รวมการเรียกบริการไว้ในโมดูล เช่น projectRepository, authService และ storageService
   - ไม่กระจาย Supabase SDK และชื่อ table ไปทั่ว React components
   - ตามสเปกละเอียด ให้ CRUD ผ่าน HTTP API ของเรา; browser ใช้ Supabase โดยตรงเฉพาะ Auth และ upload ticket ที่ได้รับอนุญาต
   - ไม่สร้าง abstraction ซับซ้อนเกินความจำเป็นของระบบทดลอง
2. **กฎธุรกิจสำคัญอยู่บน server**
   - ตรวจตัวตน เจ้าของข้อมูล โควตา AI การชำระเงิน และสิทธิ์ export บน server
   - แยกโมดูล TypeScript ของกฎธุรกิจออกจาก HTTP handler และ SDK ของผู้ให้บริการ
   - เก็บ secret และ service-role key เฉพาะ server; ถ้าใช้สิทธิ์ที่ข้าม RLS ต้องตรวจสิทธิ์เองอย่างชัดเจน
3. **ฐานข้อมูลต้องทำซ้ำและตรวจสอบได้**
   - เก็บ schema, SQL migrations และ RLS policies ใน Git
   - ใช้ PostgreSQL มาตรฐานเป็นหลัก และบันทึกจุดที่พึ่ง auth.uid() หรือบริการเฉพาะ Supabase
   - เก็บข้อมูลแบบที่เปลี่ยนตาม editor ใน JSONB ได้ แต่แยกเจ้าของงาน revision และข้อมูลที่ใช้ค้นหาเป็นคอลัมน์
4. **แยกตัวตนผู้ใช้ของแอปจาก Auth provider**
   - มีผู้ใช้/โปรไฟล์ของแอป และ mapping ไปยัง identity ของผู้ให้บริการ
   - ไม่ให้การเปลี่ยน Auth ทำให้ต้องเปลี่ยนเจ้าของโปรเจกต์และประวัติซื้อทั้งหมด
   - วางแผน session, OAuth configuration และการเข้าสู่ระบบใหม่เมื่อจะย้าย Auth จริง
5. **ไม่ผูกไฟล์กับ URL ถาวรของผู้ให้บริการ**
   - โปรเจกต์อ้าง assetId; metadata เก็บ bucket/object key และผู้ให้บริการ
   - สร้าง URL ตามสิทธิ์ตอนใช้งาน ไม่เก็บ signed URL ที่หมดอายุเป็นตัวอ้างอิงถาวร
   - สำรองฐานข้อมูลและเนื้อไฟล์แยกกัน พร้อมทดสอบกู้คืน

## ลำดับการพัฒนา

### 1. บัญชีจริงและ Cloud save

- Google login และ session จริง
- บันทึก/เปิดงานข้ามเครื่อง พร้อมกฎแยกข้อมูลแต่ละผู้ใช้
- นำงาน localStorage เดิมขึ้น cloud โดยเก็บต้นฉบับไว้จนยืนยันสำเร็จ และป้องกันนำเข้าซ้ำ
- แยกรูปไป Storage และรองรับไฟล์โปรเจกต์เดิม
- เพิ่ม revision เพื่อตรวจความขัดแย้งเมื่อแก้จากหลายแท็บหรือหลายเครื่อง
- Logout ไม่ลบงานใน cloud และต้องไม่แสดง cache ของบัญชีก่อนหน้าให้บัญชีใหม่
- เกณฑ์ผ่าน: ผู้ใช้ A อ่าน/แก้/ดาวน์โหลดไฟล์ของ B ไม่ได้ และงานเดิมไม่สูญหายระหว่างย้าย

### 2. โควตาและต้นทุน AI

- ตรวจบัญชีและสิทธิ์ก่อนเรียก AI
- จำกัดความถี่และจองโควตาแบบ atomic เพื่อรับคำขอพร้อมกันอย่างถูกต้อง
- บันทึก request ID, สถานะ, token และต้นทุน; ป้องกันคำขอซ้ำ
- กำหนดการคืนโควตาเมื่อผิดพลาด และแจ้งเตือนงบประมาณ
- เกณฑ์ผ่าน: คำขอซ้ำ/พร้อมกันไม่ทำให้ใช้เกินสิทธิ์หรือคิดซ้ำโดยไม่ตั้งใจ

### 3. การชำระเงินและสิทธิ์ใช้งาน

- รองรับการซื้อรายแบบและ subscription ก่อนขยายสู่แพ็กเกจกลุ่ม
- แยกสิทธิ์ของงานออกจากสถานะ subscription; ไม่ใช้เพียง isPremium
- กำหนดราคาและสิทธิ์บน server ไม่เชื่อค่าที่ส่งจาก browser
- ยืนยันผลจาก webhook ที่ตรวจลายเซ็นและรองรับเหตุการณ์ซ้ำ/ไม่เรียงลำดับ
- เกณฑ์ผ่าน: ปลอมสถานะจ่ายจากหน้าเว็บไม่ได้ และส่ง webhook ซ้ำไม่สร้างสิทธิ์ซ้ำ

### 4. ไฟล์ส่งออกและการทดสอบพิมพ์

- ตรวจสิทธิ์ก่อนสร้างไฟล์ส่งออกอย่างเป็นทางการ
- เก็บ snapshot ของแบบ เวอร์ชันตัวสร้างไฟล์ และไฟล์ผลลัพธ์เพื่อดาวน์โหลดซ้ำ
- ใช้ private storage และลิงก์ชั่วคราวตามสิทธิ์
- แยกโค้ด geometry ที่ไม่ผูกกับ browser; ประเมินการปรับ Canvas/DOM หรือใช้ browser worker สำหรับส่วนที่จำเป็น
- ทดสอบขนาด ฟอนต์ ภาพ และสีร่วมกับโรงพิมพ์ ไม่ถือว่าเพิ่ม backend แล้วไฟล์พร้อมผลิตโดยอัตโนมัติ

### 5. ระบบทีมและการปฏิบัติการ

- เพิ่ม workspace/membership/role ตามความต้องการแพ็กเกจกลุ่มที่ยืนยันแล้ว
- เพิ่มหน้าดูการใช้งาน รายการชำระเงิน ข้อผิดพลาด และค่า AI
- ทดสอบสำรอง/กู้คืนและกำหนดการเก็บไฟล์ตามสิทธิ์ที่ขาย

## ข้อกำหนดจากข้อเสนอที่ต้องยืนยันก่อนทำระบบขายจริง

รายการนี้เป็นแนวทางในเอกสารข้อเสนอ ไม่ใช่การยืนยันว่าพัฒนาแล้วหรือจะเปิดขายทันที:

- ซื้อรายแบบ 149 บาท; รายเดือน 390 บาท; รายปี 3,900 บาท; แพ็กเกจกลุ่ม 25,000 บาท/ปี 50 บัญชี
- รายแบบแก้โครงสร้างฟรี 7 วัน: ต้องกำหนดจุดเริ่มเวลาและสิ่งที่นับเป็นแบบใหม่ให้ชัด ไม่ตรวจจากชื่อหรือ project ID อย่างเดียว
- หลังยกเลิก subscription ยังดาวน์โหลดไฟล์ที่เคยส่งออกได้ แต่สร้างไฟล์ส่งออกใหม่ไม่ได้หากไม่มีสิทธิ์อื่น
- AI ของแพ็กเกจฟรี/รายแบบ 5 ครั้งต่อเดือน; คำว่า “ไม่จำกัด” ของแพ็กเกจสมาชิกต้องกำหนด fair use และต้นทุนให้ชัดก่อนขาย
- ยังไม่ได้เลือกผู้ให้บริการชำระเงินหรือกำหนด retention ของไฟล์อย่างเป็นทางการ

## ข้อจำกัดและความเสี่ยง

- การซ่อนปุ่ม export ไม่ใช่การป้องกัน: browser มี geometry และเส้นแบบอยู่แล้ว การย้าย export ไป server ก็ไม่ป้องกันการสร้างแบบซ้ำทั้งหมด
- ระยะแรกเน้นสิทธิ์ไฟล์ส่งออกอย่างเป็นทางการ ประวัติงาน และบริการ; หากต้องการป้องกันเข้ม ต้องประเมินการลดความละเอียด preview ซึ่งมีผลต่อ UX
- Supabase ช่วยลดงาน infrastructure แต่ยังต้องออกแบบ authorization, RLS และการทดสอบความปลอดภัย
- การย้ายออกไม่ใช่เปลี่ยน connection string อย่างเดียว: Auth, policies, Storage และงานเบื้องหลังต้องมีแผนเฉพาะ
- การใช้บริการ managed มีค่าใช้จ่ายตามการใช้งาน ส่วนระบบที่ประกอบเองเพิ่มภาระดูแล ไม่รับประกันว่าถูกกว่าหรือเร็วกว่าเสมอ

## แผนย้ายในอนาคต

1. ประเมินเหตุผลจริง เช่น กฎธุรกิจซับซ้อน งาน worker การเชื่อมโรงพิมพ์ ต้นทุน หรือข้อกำหนดด้านข้อมูล
2. เพิ่ม NestJS และย้าย API ทีละโมดูล โดยยังใช้ Supabase Auth/Database/Storage เดิม
3. เมื่อต้องย้ายฐานข้อมูล ให้ซ้อม restore ตรวจข้อมูล/สิทธิ์ และกำหนดการหยุดเขียนหรือ sync ก่อนสลับระบบ
4. ย้ายไฟล์พร้อมตรวจจำนวน ขนาด/checksum และสิทธิ์ จากนั้นเปลี่ยน storage adapter
5. ย้าย Auth แยกเป็นโครงการย่อยเมื่อจำเป็น โดยรักษา mapping ผู้ใช้และแจ้งผลกระทบต่อ session
6. ทุกขั้นต้องมี backup, rollback และการทดสอบก่อนสลับ production; ไม่ลบระบบเก่าจนตรวจสอบการย้ายสำเร็จ
