# เริ่มงาน Marketplace สำหรับทีม A และ B

เอกสารชุดนี้ใช้ส่งต่อแผนให้ผู้พัฒนาและ AI ใน repository gen-package ผู้ใช้ต้องมอบหมายบทบาทและขอบเขตก่อนเริ่มลงมือ เอกสารที่บันทึกเมื่อ 30 ตุลาคม 2026 เป็นแผนและข้อมูลตั้งต้น ยังไม่ได้สร้าง routes, Marketplace หรือ Admin ตามแผน

## อ่านตามลำดับ

1. README.md และ AGENTS.md ที่ root รวมถึงส่วนที่เกี่ยวข้องใน CLAUDE.md
2. [PLAN.md](PLAN.md) — ขอบเขต สถาปัตยกรรม และ roadmap
3. [PHASE-0-1.md](PHASE-0-1.md) — checklist จุดรอกันและการตรวจรับ
4. [HANDOFF-A.md](HANDOFF-A.md) หรือ [HANDOFF-B.md](HANDOFF-B.md) — คำสั่งสำหรับบทบาทที่ได้รับ
5. [PROGRESS-A.md](PROGRESS-A.md) และ [PROGRESS-B.md](PROGRESS-B.md) — ผลงานจริงและสิ่งที่อีกฝ่ายส่งให้
6. [CONTEXT.md](../../CONTEXT.md) — คำศัพท์ของธุรกิจ

ชื่อไฟล์ในข้อ 1 หมายถึงไฟล์ที่ root ของ checkout นั้น แต่ละ AI ต้องตรวจโค้ดที่ตนมีจริงและ commit ปัจจุบันก่อนทำงาน ไม่ถือว่าเอกสารเก่าพิสูจน์ว่า API หรือการทดสอบยังผ่าน

## วิธีส่งให้เพื่อน

ต้องให้เพื่อนมี source code และเอกสารชุดเดียวกันก่อน ข้อความในแชตหรือ path บนเครื่องผู้ส่งไม่ได้ทำให้ AI ของอีกคนอ่านไฟล์ได้เอง

### ส่งผ่าน Git

ให้ผู้รับตรวจว่ามี commit เอกสารรุ่นเดียวกันก่อนเริ่มงาน เมื่อเอกสารถูกรวมเข้า main ให้ดึง main ล่าสุดด้วย git pull --ff-only ตาม workflow ทีม แล้วใช้ข้อความเริ่มงานด้านล่าง การดึงเอกสารไม่ได้เริ่ม implementation โดยอัตโนมัติ

แต่ละคนควรทำงานคนละ branch บนฐานเอกสารเดียวกัน เช่น codex/marketplace-a-phase-1 และ codex/marketplace-b-phase-1 หากมี branch งานอยู่แล้วให้ใช้ branch ที่เหมาะสม ไม่เขียนทับงานค้างหรือ reset งานเพื่อเริ่มตามแผน

### ส่งเป็นไฟล์

ส่ง archive ของเอกสารให้เพื่อน แล้วให้วาง docs/marketplace/, AGENTS.md และ CONTEXT.md ใน repository gen-package ของเขา หากปลายทางมีเอกสารชื่อเดียวกันอยู่แล้ว ให้เทียบและรวมเนื้อหาตามรุ่น ไม่แตก archive ทับงานค้างทันที

Archive ของเอกสารอย่างเดียวไม่รวม source code, dependencies หรือ credentials เพื่อนต้องมี checkout ของโปรเจกต์ด้วย Archive ไม่เขียนทับ CLAUDE.md เดิมของเพื่อน ให้ใช้ข้อความสั่งอ่าน HANDOFF โดยตรงตามด้านล่าง ส่วนการส่งผ่าน Git มีบรรทัดชี้แผนใน CLAUDE.md ให้ด้วย

## ข้อความเริ่มงานคน A

คุณรับบทคน A ของโปรเจกต์ PackIt ให้เปิดและอ่าน docs/marketplace/HANDOFF-A.md แล้วอ่านไฟล์อ้างอิงตามลำดับ ตรวจโค้ดจริงและ PROGRESS ของทั้งสองฝ่าย เริ่มทำงานเฟส 0 ของ A แล้วลงมือเฟส 1 เฉพาะงานของ A ที่เงื่อนไขพร้อมตาม PHASE-0-1.md ทำต่อจนจบขอบเขตที่ทำได้ ไม่หยุดแค่เสนอแผน อัปเดต PROGRESS-A.md ด้วยผลจริงและหลักฐาน หากต้องรอ B ให้ระบุรหัสงานกับข้อมูลที่ขาด แล้วทำงานอิสระของ A ต่อ ห้ามทำเครื่องหมายผ่านแทน B ห้ามแก้ Figma และอย่าเริ่มเฟส 2 ขึ้นไป รอบนี้ยังไม่ commit/push หรือเปลี่ยน remote/deploy

## ข้อความเริ่มงานคน B

คุณรับบทคน B ของโปรเจกต์ PackIt ให้เปิดและอ่าน docs/marketplace/HANDOFF-B.md แล้วอ่านไฟล์อ้างอิงตามลำดับ ตรวจโค้ดจริงและ PROGRESS ของทั้งสองฝ่าย เริ่มทำงานเฟส 0 ของ B แล้วลงมือเฟส 1 เฉพาะงานของ B ที่เงื่อนไขพร้อมตาม PHASE-0-1.md ทำต่อจนจบขอบเขตที่ทำได้ ไม่หยุดแค่เสนอแผน อัปเดต PROGRESS-B.md ด้วยผลจริงและหลักฐาน ส่ง API contract และข้อมูลทดสอบให้ A ตั้งแต่พร้อม หากต้องรอ A ให้ระบุรหัสงานกับข้อมูลที่ขาด แล้วทำงานอิสระของ B ต่อ ห้ามทำเครื่องหมายผ่านแทน A ห้ามแก้ Figma และอย่าเริ่มเฟส 2 ขึ้นไป รอบนี้ยังไม่ commit/push หรือเปลี่ยน remote/deploy

ข้อความเริ่มงานเหล่านี้อนุญาตให้ AI ของผู้รับลงมือพัฒนาในขอบเขตที่ระบุ เมื่อผู้รับนำไปใช้จริง หากต้องการเพียงตรวจแผน ให้เปลี่ยนเป็นคำสั่ง “อ่านและตรวจแผนเท่านั้น ยังไม่แก้ไฟล์” อย่าใช้ข้อความเริ่มพัฒนาโดยไม่ตั้งใจ

## การรับส่งงานระหว่างสองเครื่อง

- ใช้ API contract และตัวอย่างข้อมูลรุ่นเดียวกัน B เป็นผู้รวมสัญญา A เป็นผู้ตรวจการใช้งาน
- เมื่อแก้สัญญาให้ระบุรุ่น/commit ที่อีกฝ่ายต้องรับ พร้อมผลกระทบ อย่าเปลี่ยนชื่อฟิลด์แล้วให้เพื่อนเดา
- ส่ง PROGRESS และหลักฐานของตนผ่าน workflow ที่ทีมใช้จริง เช่น commit/PR ที่ได้รับอนุญาต หรือไฟล์แนบ ไม่ถือว่าไฟล์ในอีกเครื่องซิงก์มาแล้ว
- ไม่วาง token, secret, ข้อมูลผู้ใช้จริง หรือ env จริงในสัญญา ตัวอย่างข้อมูล หรือรายงานผล
- ตรวจรับ integration เมื่อรวมโค้ดของทั้งสองฝ่ายใน checkout ทดสอบแล้ว หน้า mock หรือผลทดสอบจาก branch เดียวไม่พิสูจน์ integration ทั้งระบบ
- เปิด Phase 1 ร่วมกันเมื่อเงื่อนไข Phase 0 ตาม PHASE-0-1.md ผ่านจากหลักฐานของทั้งสองคน ระหว่างรอ ให้ทำงานตรวจสอบและเตรียมข้อมูลที่เป็นอิสระต่อ

## สถานะและหลักฐาน

ใช้สถานะ TODO, IN_PROGRESS, WAITING, READY_FOR_REVIEW, DONE หรือ NOT_RUN ตามความจริง DONE ต้องมีหลักฐานตามเกณฑ์งาน ส่วน WAITING ต้องมีชื่อสิ่งที่รอ เจ้าของ และงานอื่นที่ทำต่อได้

เอกสารแผนใช้เป็นขอบเขต ไม่ใช่การอนุญาตให้ทำงานภายนอกเกินคำสั่งผู้ใช้ เมื่อผู้ใช้เปลี่ยนขอบเขต ให้บันทึกการเปลี่ยนนั้นและปรับแผนให้ตรงโดยไม่ขออนุญาตซ้ำสำหรับสิ่งที่อนุญาตแล้ว
